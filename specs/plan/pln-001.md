## Proposed ADR-0001 decision text

- **Provider:** Supabase Auth.
- **Sessions:** cookie-based via `@supabase/ssr`. `src/proxy.ts` refreshes and
  verifies tokens with `supabase.auth.getClaims()`; the DAL uses
  `supabase.auth.getUser()` for secure checks. Never trust `getSession()` for
  authorization.
- **Identity ownership:** Supabase owns `auth.users`, credentials, email
  verification, and sessions. The app database owns `profiles` and roles in a later
  phase, keyed by `auth.users.id`. No passwords stored in the app database. Role is
  never read from `user_metadata`.
- **Roles:** self-registration creates patient accounts only. Doctor/admin accounts
  are provisioned by admins. No role picker on registration. Role-aware navigation
  is deferred until roles exist in the app database.
- **CSRF:** auth mutations go through Server Actions (Next.js built-in Origin/Host
  check) with `SameSite=Lax` cookies. `/auth/callback` is a GET that sets a session
  but is protected by PKCE (single-use code + code verifier). No state-changing GETs
  otherwise. No separate CSRF token for auth forms.
- **Env:** `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`
  (public-safe by design). No service-role key in this slice.
- **Test strategy:** mock the Supabase client in unit/component tests; manual smoke
  test against the hosted dev project with synthetic users.

## Behavior

- **Login** (`/login`): zod-validate email/password → `signInWithPassword` → on
  success redirect to sanitized `next` (default `/account`); on failure return
  generic "Email or password is incorrect." Preserve email input, never password.
- **Register** (`/register`): zod-validate full name/email/password/confirm →
  `signUp` with `full_name` in metadata and `emailRedirectTo` pointing at
  `/auth/callback?next=/account` → on success show neutral confirmation ("If an
  account can be created for this email, check your inbox.") or redirect directly if
  a session is returned (email confirmation disabled). No account enumeration.
- **Callback** (`/auth/callback`): exchange PKCE code, redirect to sanitized `next`;
  failures → `/login?error=callback`.
- **Account** (`/account`): `requireUser` via `getUser()`; placeholder page shows the
  signed-in email + sign-out button. Proxy redirects unauthenticated visitors to
  `/login?next=/account`; the DAL re-checks even if the proxy is bypassed.
- **Sign-out**: server action calls `signOut()`, clears cookies, redirects `/login`.

## Security

- Proxy does refresh + optimistic redirect only. Authorization is enforced in the
  DAL and actions, never by middleware/proxy or UI visibility.
- No raw provider error text, no password logging, no account enumeration.
- Supabase session cookies are not HttpOnly by design (the browser needs the refresh
  token). XSS risk is documented; a CSP is planned for a later phase.
- `Cache-Control: private, no-store` on session-mutating responses
  (`A-CACHE-01`): callback redirect and `/account`.
- Return path sanitization: allow same-origin relative paths only; reject `//`,
  backslashes, absolute URLs, and non-path schemes (e.g. `javascript:`).

## Error mapping (user-safe)

Supabase codes → messages: `invalid_credentials` → generic credential error;
`email_not_confirmed` → "Confirm your email first"; `user_already_exists` →
neutral registration message; `weak_password` → password policy message;
`over_email_send_rate_limit` / `over_request_rate_limit` → "Too many attempts, try
later"; unknown/network → generic "Unable to sign in right now." Never pass raw
provider text to the client.

## Accessibility

- Real `<label>`s, `aria-describedby` for errors/help text, `aria-live` for
  form-level messages, `role="alert"` on error summary, focus moved to the error
  summary or first invalid field after a failed submit.
- Autocomplete attributes: `email`, `current-password`, `new-password`, `name`.
- Submit buttons disabled while pending, with clear pending text.
- WCAG 2.1 AA intent; no color-only cues.

## Out of scope

Password reset, OAuth/social login, MFA, database roles/profiles, role-aware
navigation, 401/403 flows, E2E (no Playwright), admin user management, real patient
data. `UC-AUTH-03`, `UC-AUTH-04`, and the `A-AUTH-*` route-handler tests are
deferred until API routes and roles exist.

## Known limitations

- Without a Supabase dev project/env, real auth cannot be verified end-to-end;
  tests use mocks only. Report this explicitly if env is not provided.
- Role assignment (patient default) is enforced by policy (no role picker, staff
  accounts not self-provisioned) until app-DB roles exist.
