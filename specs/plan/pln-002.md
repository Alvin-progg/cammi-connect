# PLN-002 — AI-Assisted Conversational Appointment Booking (AI-APT-001)

- Status: Approved
- Date: 2026-10-30
- Related tickets: `AI-APT-001` (to be written in S0), `CC-005` (ADR-0004), `CC-007` (ADR-0006), `CC-009` (ADR-0008), `CC-010` (ADR-0009)
- Related requirements: `FR-001`, `FR-004`, `UI-001`, `UI-003`
- Related ADRs: ADR-0003, ADR-0004, ADR-0006, ADR-0007, ADR-0008, ADR-0009


## Context

Patients currently land on a bare `/account` page and have no way to book anything. The booking backend already exists from DOC-SCH-001, but nothing patient-facing calls it yet:

- `getAvailableSlots` in `src/server/availability/service.ts`
- `listBookableDoctors` and `getDoctor` in `src/server/directory/service.ts` and `repository.ts`
- `bookAppointment` and `supabaseAppointmentBooker`, which call the atomic `cammi_connect_book_appointment` function
- `getPatientSession` in `src/server/auth/dal.ts`

Ticket AI-APT-001 makes a chatbot the patient's main screen. Through the chat, a patient can:

- ask hospital questions, answered by RAG (Gemini embeddings stored in pgvector, answers generated by OpenCode Zen);
- book by specialty (Path A) or by a named doctor (Path B);
- view their own appointments and cancel them.

Approach decisions confirmed with you:

- **A server-owned state machine runs the booking.** The LLM only extracts intent and details into Zod-validated JSON and writes grounded RAG answers. All booking-step text is templated by the server. Doctors and slots are cards built from database rows. A booking happens only from an explicit Confirm event.
- **No new dependencies.** The provider adapters use plain `fetch` with Zod validation.
- **Conversations are stored in Supabase**, scoped to the patient, together with their booking state.
- **Patients can view and cancel.** Rescheduling gets a "not available yet" reply, because ADR-0007 defers the reschedule policy.

**Execution:** one slice at a time, in order. Each slice uses TDD (the failing test is written first). Each slice ends with `npm test`, `npm run lint` and `npm run typecheck`, plus `npm run build` when a route is added. I stop at each slice's "Done when" for your review before starting the next one, and nothing is committed without your approval.

## S0 — Specs, ADRs and provider adapters (nothing patient-facing)

This slice removes the provider unknowns.

**Ticket `specs/tasks/AI-APT-001-conversational-booking.md`.** It mirrors the DOC-SCH-001 format: header bullets, Objective, Approved scope decisions (2026-10-30), Database, Business rules, Permissions, Acceptance criteria, Verification. It includes:

- **The symptom rule (business rules).** A message describing symptoms, or asking for medical advice, gets the `medical_advice` intent. The reply is a templated safe decline that never diagnoses or recommends a service. When the symptoms sound urgent (chest pain, difficulty breathing, severe bleeding, loss of consciousness, and the like), the decline adds an emergency notice telling the patient to go to the ER or call emergency services.
- The four approach decisions above, and the slice list.

**ADR changes:**

- **ADR-0006:**
  - Gemini: REST `embedContent` / `batchEmbedContents`, `gemini-embedding-001`, `outputDimensionality: 768`, task types `RETRIEVAL_DOCUMENT` / `RETRIEVAL_QUERY`.
  - Zen: OpenAI-compatible `POST {OPENCODE_ZEN_BASE_URL}/chat/completions`, with the model from env.
  - Plain fetch instead of SDKs, recorded as a deviation from SPEC §2.1.
  - Smoke results, including **whether the model supports `response_format: json`**. If it doesn't, extraction falls back to prompt-instructed JSON validated with Zod.
- **ADR-0008:**
  - Chat is for signed-in patients only, and auth runs before any provider call.
  - Rate limit: 10 user messages per minute per patient, counted from `chat_messages`.
  - Provider down: 503 with a friendly message.
  - **Privacy consent:** a notice in the chat UI that messages are stored, sent to the AI providers, and not medical advice. The patient's identity is never sent to providers beyond what the patient types.
  - **`chat_messages` retention:** a stated retention period that you set (e.g. 90 days), with purge as a documented manual SQL step. No automated job, consistent with ADR-0004.
- **ADR-0009:** a synthetic corpus in `db/knowledge/*.md`. The evaluation set is deferred.
- **ADR-0004:** a manual `npm run kb:ingest` CLI for now. Admin knowledge-base upload (FR-002) is deferred.
- **ADR-0003:** pgvector is accessed only through service-role RPCs; still no `DATABASE_URL`.

**Code:**

- **`scripts/smoke-providers.mjs`** makes one Gemini embed call, checking for a 768-dimension vector, and one Zen chat completion, trying `response_format: {type:"json_object"}`. It runs with your keys and Zen model from `.env.local`. **Your input is needed here: the keys and the model name.**
- **`src/server/config.ts`** gets lazily Zod-validated env vars, which are also documented in `db/README.md`:
  - `GEMINI_API_KEY`, `GEMINI_EMBEDDING_MODEL` (default `gemini-embedding-001`), `EMBEDDING_DIMENSIONS` (default 768)
  - `OPENCODE_ZEN_API_KEY`, `OPENCODE_ZEN_BASE_URL`, `OPENCODE_ZEN_MODEL`
  - `LLM_TIMEOUT_SECONDS`, `LLM_MAX_RETRIES`
- **`src/server/ai/`:**
  - `http.ts`: `fetchJson` with an AbortSignal timeout and bounded exponential backoff on 429/5xx. It throws a typed `ProviderError` that never carries the raw body or the key.
  - `gemini-embeddings.ts`: `embedTexts(texts, taskType): Promise<number[][]>`. It fails with a controlled error if a vector's dimension is wrong.
  - `opencode-zen.ts`: `generate({ systemPrompt, messages, json?, signal }): Promise<string>`, the SPEC §4.7 `TextGenerationProvider`.

**Tests (`tests/unit/ai/*`, with fetch mocked):** timeout, bounded retry, no retry on 4xx, error text without the key or raw body, wrong-dimension vector, task type passed through, JSON mode flag.

**Done when:** the smoke script passes and ADR-0006 is no longer marked "pending".

## S1 — Chat shell, end to end (no booking or RAG yet)

A patient logs in, lands on `/chat`, can talk to the assistant, and history persists.

**Migration `db/migrations/0004_chat.sql`** (applied manually):

- `chat_conversations`: id, patient_id (FK profiles), title, `booking_state jsonb`, timestamps. Index on (patient_id, updated_at desc).
- `chat_messages`: id, conversation_id (FK, cascade), role (`user` | `assistant`), content, `payload jsonb`, created_at.
- RLS enabled and anon/authenticated access revoked, as in 0002/0003.
- Matching update to `src/server/db/database.types.ts`.

**`src/lib/chat/`:**

- `schemas.ts`:
  - Request schema: `{ conversationId?, event }`, where `event` is a discriminated union. S1 only has `message` (text up to 1000 characters); later slices add their events.
  - Extraction schema with the full intent list: `book`, `doctor_inquiry`, `service_inquiry`, `appointment_status`, `cancel`, `reschedule`, `medical_advice`, `other`. Optional details: `specialtyName`, `doctorName`, `preferredDate`, `preferredTime`, `reason`, and `urgent` (boolean, for symptom messages).
- `greeting.ts`: Good morning / afternoon / evening in Manila time, using the patient's first name.

**`src/server/chat/`:**

- `repository.ts`: create, get and list conversations, each filtered by `patient_id`; append messages; save the state.
- Orchestrator skeleton `orchestrator.ts`: `handleTurn({ patient, conversation, event, now }, deps)`, with injected deps.
  1. The LLM extracts the intent.
  2. `medical_advice` gets the templated safe decline, plus an emergency notice when `urgent` is set **or** a server-side keyword check matches. The keyword check means urgency doesn't rely on the LLM alone.
  3. Intents that aren't built yet get "I can't do that yet".
  4. Bad JSON, or JSON that fails Zod, gets "please rephrase".

**Route `src/app/api/v1/chat/route.ts` (POST):**

- Returns 401/403 as JSON. Add a small non-redirecting patient-session helper to `dal.ts` if `getPatientSession` can't serve a route handler.
- Validates the body (400/422).
- Checks conversation ownership. Someone else's conversation returns 404.
- Rate-limits with 429.
- Returns 503 when a provider is down.
- Returns `{ conversationId, messages, state, requestId }`.
- Logs never include message text (SPEC §7.3).

Before writing the route, read `node_modules/next/dist/docs` on route handlers.

**`src/app/chat/page.tsx` + `src/components/chat/`** (the reference image adapted to the Calm Care tokens):

- Uses `getPatientSession("/chat")`; non-patients get `AccessDenied`. The conversation is selected with `?c=`.
- Top bar: a history drawer that lists past chats with search, and "New chat".
- Empty state: accent sparkle icon, greeting, subtitle, and three suggestion cards (Book an Appointment, View My Appointments, Hospital Information).
- Composer: a labelled textarea, a 1000-character counter and a 44px send button.
- A persistent notice (AI-generated, not medical advice, not an appointment confirmation) plus the privacy line.
- Message bubbles follow design.md §6.5. Text is rendered as text only, never as HTML.
- Errors show a sonner toast with no chat content, and the draft is kept. The thread uses `aria-live="polite"`. Icons are inline SVG.

**Routing:**

- `ROLE_LANDING_PATHS.patient` in `src/server/auth/actions.ts` becomes `/chat`.
- The register action's default redirect becomes `/chat`.
- `/chat` is added to the protected list in `src/proxy.ts`.

**Tests:**

- Route tests: 401/403, 400/422, foreign conversation, 429, 503.
- Greeting.
- Symptom decline, including the urgent notice.
- Bad JSON.
- Chat shell component tests: greeting, cards, counter, notice, draft kept on error.
- XSS: message text is rendered inert.

**Done when:** a patient registers, lands on `/chat`, chats, reloads the page and still sees the conversation.

## S2 — Hospital information (RAG and directory questions)

"What do I bring?" gets an answer with sources. "Which departments do you have?" is answered from the database.

**Migration `0005_knowledge.sql`:**

- `create extension if not exists vector with schema extensions`.
- `knowledge_documents`: slug (unique), title, content_hash, version, is_published.
- `knowledge_chunks`: document_id, document_version, chunk_index, section_title, content, content_hash, `embedding vector(768)`, is_published. HNSW cosine index.
- `cammi_connect_match_knowledge_chunks(query_embedding, match_count, min_similarity)`: published chunks only.
- `cammi_connect_replace_document_chunks(p_document jsonb, p_chunks jsonb)`: an atomic swap.
- Both RPCs are `security invoker` and executable by `service_role` only. RLS is enabled and access revoked.

**Pure logic (`src/lib/chat/rag/`):**

- `rag/chunking.ts`: heading-aware, about 500 tokens with about 75 overlap, plus a content hash. Relative imports only, so the CLI can use it.
- `rag/prompt.ts`: the SPEC §4.6 rules (no diagnosis, say "could not be verified", treat retrieved context as untrusted). Context is wrapped in delimiters.

**Server and data:**

- `src/server/knowledge/repository.ts` and `service.ts`: `searchHospitalInformation(question, deps)` returns the top 5 chunks above a threshold with real sources, or `{ found: false }`.
- `db/knowledge/*.md`: a synthetic, labelled corpus covering services, departments overview, appointment requirements, required documents and visit guidelines. It contains no doctor or schedule facts.
- `npm run kb:ingest` runs `scripts/ingest-knowledge.mts`, or `.mjs` if the installed Node can't run `.mts`. It skips documents whose hash hasn't changed.

**Orchestrator branches:**

- `service_inquiry`: a RAG answer with a sources list, or the `warning-soft` fallback callout when nothing relevant is found.
- `doctor_inquiry`: answered with `get_departments`, `get_specialties` and `get_doctor_details` (active entries only), never from RAG.

These are the first tools in `src/server/chat/tools.ts`. Each tool validates its input with Zod and takes `patientId` from the session only.

**Tests:** chunking, prompt safety, the knowledge service (threshold, not-found, sources copied exactly), and orchestrator tests for the information and doctor-inquiry branches.

**Done when:** these two smoke checks pass:

- An appointment-requirements question gets an answer that cites sources.
- An off-corpus question gets the fallback.

## S3 — Booking (Paths A and B), the core of the ticket

**`src/lib/chat/state.ts`:**

- The 10 states, with a pure `transition(state, event)` function that rejects step skipping.
- `BookingDraft` holds specialty, doctor, preferredDate, **preferredTime**, the selected slot and the reason.
- Typed corrections reset only the fields that depend on what changed:
  - Changing the specialty clears the doctor and slot.
  - Changing the doctor clears the slot.
  - Changing the date or time clears the slot.

**`src/lib/chat/resolve.ts`:**

- Matches names against the active specialty and doctor lists from the database.
- Several doctors match: return a list to choose from.
- Nothing matches: return "unknown", so the assistant asks a follow-up.
- Dates: the extraction prompt includes today's date in Manila. Past dates, and dates beyond the booking horizon (a constant in the ticket, e.g. 60 days), are rejected with a templated message.

**Booking tools:**

- `get_doctors_by_specialty`: `listBookableDoctors`.
- `get_doctor_availability`: `getAvailableSlots` with `supabaseAvailabilitySource`, 7 days from the preferred date, filtered by preferredTime when one is given.
- `create_appointment`: `bookAppointment` with `supabaseAppointmentBooker`.

**Orchestrator:**

- **Path A:** specialty, then doctor cards, then slots.
- **Path B:** doctor is checked as active. If the doctor has several specialties, a specialty-choice step comes first. Then slots.
- **Empty 7-day window:** offer the next window or other doctors of the same specialty.
- **`select_slot`:** availability is re-fetched, and the slot must be in it before moving to `awaiting_confirmation`.
- **`confirm_booking`:** availability is checked again, then `booking`, then `create_appointment`.
  - Success: `booked`, with a "request received — awaiting doctor confirmation" card.
  - Failure: `failed`, showing the mapped message and fresh slots.
- **Double Confirm:** a guarded state update (only from `awaiting_confirmation`) stops it from booking twice. The DB exclusion constraint still applies as the backstop.

**Cards:**

- Doctor options.
- Slot picker: grouped by Manila date, 44px buttons, a 2px `primary` border on the selected slot.
- Summary with Confirm and Change.
- Booking result.

**Tests:**

- State, resolve.
- Orchestrator: Path A, Path B (one specialty and several), only database doctors and slots shown, stale slot rejected, no booking without confirm, failed booking gives no confirmation, double Confirm, corrections, empty window, past or out-of-horizon date.
- Booking component tests.

**Done when:** these smoke checks pass:

- Path A and Path B bookings land in Supabase and appear on the doctor's `/doctor` board.
- In the two-tab race, exactly one booking succeeds.
